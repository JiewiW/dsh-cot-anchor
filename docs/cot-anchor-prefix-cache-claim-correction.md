# cot-anchor 前缀缓存论断更正 — release 文档修改指引

> **TL;DR**：README 与 RELEASE-NOTES 断言「纪律常量前置可命中 KV 前缀缓存」，该论断**不成立**。注入走纯尾部追加（`surfaceOp: "append"`），两种顺序在缓存行为上**等价**；前缀缓存按 token 位置匹配，固定文本出现在新位置时无法复用旧位置的 KV，**每个注入块都必然在首现的那次请求上未命中一次**。需删除 4 处错误因果表述、修正 2 行表格口径、改写 1 处代码注释与 1 个补丁脚本，并新增一条更正记录。连带发现：成本表的「注入占会话未命中输入 1.12%」口径错误，按正确口径约为 **5.6%**（待实测复核）。

## 2 源码实证（改写依据）

注入链路全程只有追加，不改写任何已有节点：

| 环节 | 位置 | 语句 |
| --- | --- | --- |
| 插件产出 | `dsh-cot-anchor/lib/index.js:3346`、`:3351` | `additionalContexts: [execDisciplineContext, anchor, ...]` |
| 内核收下 | `dsh-agent-loop/lib/index.js:583` | `for (const context of result.additionalContexts ?? []) acceptContext(context);` |
| 入待发队列 | 同文件 `:1263` | `this.inbox.splice("next-step", this.inbox.nextStep.length, 0, [context])` |
| 取出 | 同文件 `:114` | `claim()` 内 `mutate("next-step", 0, this.nextStep.length, [], false)`（纯排空，不重排） |
| 落历史 | 同文件 `:1074` | `session.append("user/message", message, { surfaceOp: "append" })` |

内核中唯一会打穿前缀的写法是 `surfaceOp: "replace"`（同文件 `:283`–`:306`），仅由 system prompt 投影使用（compaction、system prompt 变更），cot-anchor 不经过该路径。

三条推论（改写依据）：

- **P1** 尾部追加不改变已有 token 序列，因此除新追加块外，此前内容仍是稳定前缀，持续命中。
- **P2** 新追加块在其首现的那次请求上必然未命中（全新 token），此后成为前缀的一部分转为命中。
- **P3** 前缀缓存按 token **位置**匹配，同一段固定文本出现在新位置时无法复用其旧位置的 KV；因此「文本是否固定」不产生任何缓存收益，顺序 `[纪律, 锚点]` 与 `[锚点, 纪律]` **等价**。

实际成本控制来自注入频率闸门：纪律块与锚点共用同一推理指纹去重（`injectedReasoningBySession`，`dsh-cot-anchor/lib/index.js:3309`），把注入从"每次工具调用"压到"每次推理指纹变化"，两者恒为 1:1 成对出现。

## 4 替换文本草稿

**D1 — `RELEASE-NOTES.md` 新增更正小节（置于最新版本小节之前）**

```markdown
## 更正 — v0.1.1「纪律常量前置命中前缀缓存」论断撤回

v0.1.1 声称把纪律常量排到注入数组最前可命中 KV 前缀缓存。经核对宿主注入链路，该论断不成立：插件注入全程以 `surfaceOp: "append"` 在会话日志尾部追加 `user/message`，不改写已有节点；前缀缓存按 token 位置匹配，固定文本出现在新位置时无法复用旧位置的 KV。顺序 `[纪律, 锚点]` 与 `[锚点, 纪律]` 在缓存行为上等价，v0.1.1 的顺序调整不产生缓存收益。

保留该顺序仅为注入内容排列的一致性，与成本无关。真正控制成本的是纪律块与锚点共用的推理指纹去重闸门：注入频率等于指纹变化频率，两者 1:1 成对出现。v0.1.1 表格中的体积占比数据不受影响，但其中「具备缓存命中条件」的结论作废。
```

**D2 — `RELEASE-NOTES.md:25` 替换**

```markdown
**原因**：纪律文本与推理锚点共用同一推理指纹去重闸门，两者恒为 1:1 成对注入；顺序调整仅为排列一致性，不改变缓存行为（该论断已于后续版本更正）。
```

**D3 — `README.md:91` 替换**

```markdown
注入消息会随之后续请求的上下文一同发送，因此持续占用少量上下文窗口。按中英混排估算，660 字符约合 200–500 token 量级——相对于一次工具往返的上下文可以忽略，但它在**每一步**都会累积。注入以尾部追加方式写入会话日志，不改写已有内容，因此不会打穿前缀缓存：除新追加的一块外，此前内容始终是稳定前缀。新追加块在其首次出现的那次请求上按未命中计费一次，此后转为缓存命中——这一点与文本是否固定无关。
```

**D4 — `README.md:106` 替换**

```markdown
结论：插件带来的新增输入在全会话 token 总量的 0.3% 以内。每个注入块在首现时按未命中计费一次，此后随上下文增长参与后续每一次请求。纪律块体积占注入量约五分之四，但"文本固定"不带来额外缓存收益——该占比只反映体积，不反映命中。
```

**V3 成本数字复核**（仅当保留成本表时执行）

口径：设第 i 个注入块体积为 `S_i`、首现于第 `k_i` 次请求、该会话共 `N` 次请求，则

- 未命中量 = `Σ S_i`（每块各首现一次）
- 缓存读取量 = `Σ S_i × (N − k_i)`

按现有数据 `Σ S_i = 21,436`，故未命中占比 = `21,436 / 379,969 ≈ 5.6%`。该数值为按正确口径重算的结果，**必须在会话日志上实测确认后方可写入对外文档**；实测前一律标注【待实测】。
